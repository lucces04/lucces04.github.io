Go 的错误处理看起来重复，重复本身不是问题。问题是每一层都把错误变成一句新的散文，调用方既不能判断，日志里也拼不出完整路径。

## 调用方要能分支

如果上一层需要决定重试、跳过还是失败，错误里就得有可判断的信息。我用 `errors.Is` 和 `errors.As` 表达这种分支，而不是比较错误字符串。

字符串会在某次文案修改之后悄悄失效。哨兵错误和自定义类型更稳，也方便测试。

## 包装时留下动作

包装文案我固定写成「谁在做什么，关键参数是什么」。不要只写 `failed`。下面是读配置和打开存储时的样子。

```go
func open(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return fmt.Errorf("open config %s: %w", path, err)
    }
    defer f.Close()
    return nil
}
```

`%w` 保留了原来的错误，外面的句子补上了路径。排错的人不用再猜是哪一个文件。

## 什么时候直接返回

底层函数已经把语境写清楚时，中间层可以原样返回。再包一层 `handle error`，只是把栈上的句子变长。

我用一个简单标准：这一层有没有新增上下文。有路径、有请求编号、有用户输入的标识，就包装。没有，就 `return err`。

## 日志和返回值不要各写一遍

同一条错误如果在底层打了日志又向上返回，入口处往往会再打一次。一次请求在日志里出现三遍，值班的人反而找不到头。

我的约定是：库和业务函数只返回错误，进程入口或 HTTP 边界记录一次。记录时带上请求编号，这样能和访问日志对上。

错误文本里也不要放密钥、cookie 和整段请求体。能定位问题的，通常是动作和资源标识，不是用户原文。
